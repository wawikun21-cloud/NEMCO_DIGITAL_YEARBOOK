# Plan: Fix 500 Error on User Creation in Vercel (Serverless)

## Problem

`POST /api/admin/users` returns 500 in production (Vercel). The root cause is that Vercel does **not** run the Express server (`server/src/server.js`) — it uses the serverless entry point at `api/index.js`. The `api/index.js` file contains its own `handleCreateUser` function, which has several bugs that cause the 500.

## Root Causes (in `api/index.js`)

1. **No input validation** — `handleCreateUser` (line 352) directly destructures `req.body` without validating. Missing `student_number`, `email`, or `full_name` causes Supabase auth call to fail with an unhandled error.
2. **No duplicate-check on `student_number`** — The unique constraint on `profiles.student_number` in Supabase throws a raw Postgres error (`23505`) when a duplicate is inserted, which surfaces as a 500 instead of a 409.
3. **No try/catch around the whole flow** — If `supabaseAdmin.auth.admin.createUser` throws unexpectedly, the catch block at line 370 returns `error.message` which may be undefined, causing a generic 500.
4. **Profile upsert sends `id` field from body** — If the client sends extra fields (like `id`), the upsert may conflict or fail.
5. **No `display_name` fallback** — `full_name.split(" ")[0]` crashes if `full_name` is empty/undefined.
6. **Response shape mismatch** — `handleCreateUser` returns `{ user: authUser.user, profile }` but the client (`userService.js:95`) expects `data.user` (the profile), not the auth user object. The client then sets this as the new user in state, causing downstream issues.

## Affected Files

- `api/index.js` — serverless entry point (primary fix target)
- `client/src/services/userService.js` — client-side error handling (secondary)
- `client/src/components/admin/UserFormModal.jsx` — client-side validation (already exists, but can be hardened)

## Implementation Steps

### Step 1: Add input validation to `handleCreateUser` in `api/index.js`

Add a Zod schema (or inline validation) at the top of `handleCreateUser` to validate `student_number`, `email`, and `full_name` before any database calls. Return 400 with a clear message on validation failure.

```js
const createUserSchema = z.object({
  student_number: z.string().trim().regex(/^\d{7}$/, "Student number must be exactly 7 digits"),
  email: z.string().trim().email("Invalid email format"),
  full_name: z.string().trim().min(2, "Full name must be at least 2 characters"),
}).strict()
```

Parse `req.body` through the schema before proceeding.

### Step 2: Add duplicate `student_number` check with proper error handling

Before calling `supabaseAdmin.auth.admin.createUser`, query `profiles` for existing `student_number`. If found, return 409 with `"Student number already exists"`.

Also wrap the `createUser` auth call in a try/catch that handles Supabase-specific errors:
- `already registered` → 409
- Other errors → 400 with the actual message

### Step 3: Sanitize the profile upsert payload

Explicitly pick only the allowed fields for the `profiles` upsert instead of spreading `...profileFields` from the raw body. This prevents unknown columns from causing a Supabase error.

```js
const { student_number, email, full_name, year_level, course_or_strand, section, role, status, profile_status, bio, quote } = req.body
```

### Step 4: Add `display_name` fallback

```js
const display_name = full_name?.trim()?.split(" ")[0] || ""
```

### Step 5: Fix response shape

Return `{ user: profile }` (not `{ user: authUser.user, profile }`) so the client receives the profile object consistently.

### Step 6: Harden the catch block

Ensure the catch block always returns a meaningful message:

```js
catch (error) {
  const status = error.status || 500
  const message = error.message || "Failed to create user"
  if (status === 500) console.error("[CREATE_USER]", error)
  return json(res, status, { message })
}
```

### Step 7: Add client-side error handling improvements in `userService.js`

The existing `createUser` in `userService.js` already handles errors properly, but add a check for network-level failures (e.g., the fetch itself fails):

```js
if (!response.ok) {
  const data = await response.json().catch(() => ({}))
  throw new Error(data.message || "Failed to create user")
}
```

### Step 8: Add client-side error toast for network failures in `ManageUsersPage.jsx`

The existing `handleSubmit` already catches errors and shows a toast. No changes needed here — the existing code is sufficient.

## Validation Plan

1. **Local test**: Use the existing `api/index.js` locally with `node api/index.js` and test `POST /api/admin/users` with:
   - Valid payload → expect 201
   - Missing `student_number` → expect 400 with validation message
   - Duplicate `student_number` → expect 409
   - Invalid email → expect 400
   - Missing `full_name` → expect 400

2. **Vercel deploy**: After merging, test the same scenarios against the production endpoint.

3. **Edge cases**:
   - `student_number` with non-digits → 400
   - `email` without `@` → 400
   - `full_name` with 1 character → 400
   - Extra unknown fields in body → ignored (via explicit pick, not `strict()`)

## Risks

- **Breaking change**: If any other client relies on the old response shape `{ user: authUser.user, profile }`, it will break. Verify no other consumers exist.
- **Supabase RLS**: The `profiles` table must allow insert for the service role key (it does, since service role bypasses RLS).

## Out of Scope

- Fixing the Express server (`server/src/controllers/userController.js`) — it is not used in Vercel deployments.
- Adding rate limiting or CAPTCHA.
- Adding email verification flow.
